What changes in the experience

Focused screens replace long forms.

Search is separate from vehicle selection. Confirmation gives optional controls their own sheets. No functionality has to live on the same page to remain available.

The action stays within reach.

App navigation and primary actions have dedicated space. On small screens or with large text, one content region may scroll; the page never becomes a stack of unrelated panels.

The trip determines the screen.

Requested, accepted, arrived, in-progress and completed states each show the next useful action. Unavailable actions stay unavailable under the current backend rules.

Design and device behaviour are separate gates.

A good screenshot does not prove native GPS, keyboard, background location or payment behaviour. Each needs an on-device acceptance check before cutover.

Feature coverage — nothing silently disappears

This inventory combines the current source and project feature documentation. The interactive prototype demonstrates navigation and sample interactions. It is not a claim that native API integration or production provider verification is complete.

Rider booking & trip products

New home: Ride → search → choose → review. Planning and optional features have dedicated screens or sheets.

  • GPS, Places search, pickup/destination pins, saved places, recent destinations, airport/rail hubs and voice entry.
  • Bike, auto, mini, sedan, SUV; quote expiry/refresh, route alternatives (Fastest vs. Toll-free OMR), surge, fare breakdown and promo codes.
  • Hop Commute corridor carpooling (office routes, recurring departure windows, verified co-riders, shared expense contributions).
  • Multi-stop, rental hours, outstation/return trips and scheduled rides.
  • Fare negotiation/counter-offers, shared rides, women-driver eligibility, favourite-captain priority and booking for others/family.
Prototype: booking, sample search, selection, route alternatives, Hop Commute corridors, options, planning, matching and counter-offer previews.

Native gate: exact request serialization, current quote rules, map SDK, native speech/location and server validation.

Rider live trip & completion

Prototype: radar matching, tracking, two-way chat, RideCheck safety, payment selection, receipt and rating previews.

Rider account, money & companion features
  • Phone/OIDC sign-in, exact-number verification, profile/portrait, business fields and private media.

  • Family invitations, favourites, referrals/rewards, notifications, language, low-data and accessibility.

Prototype: all destination screens; local-only form, inbox and balance interactions.

Captain onboarding & account
  • Verified mobile, portrait, vehicle details, identity/licence/RC/insurance evidence.
  • Four-step server-side draft, corrections, operator review, expiry and re-review restrictions.
  • Vehicle-change request, private documents, profile, account and preferences.

Captain dispatch, driving & productivity
  • Online/offline, accurate/fresh location, background service, heads-up request notifications, and multi-offer candidate switching.
  • Expiring offer countdown timer (15s dispatch window), offer display acknowledgement, accept/decline, counter-offer.
  • First-accept-wins race condition handling (superseded offer notices with non-punitive ranking protection).
  • Pickup arrival, 6-digit code verification (with test autofill), start/complete.
  • Fullscreen Cockpit Navigation HUD (turn maneuvers, speed telemetry, heading compass, lane indicators).
  • Navigation, voice/traffic/map options, waiting charges, chat/contact and safety.
  • Operating Service Area selection and operator approval change requests.
  • Radius/minimum fare, go-home mode/usage limits, daily goal, break reminder and demand zones.
Prototype: offline → heads-up request (15s timer, multi-offer, race condition) → pickup → verify (autofill) → trip (Cockpit HUD) → settle, plus service area and tools/settings.

Native gate: physical-device location/power behaviour, atomic acceptance, push/reconnect, code attempts and server transitions.

Captain money, history & insights
  • Dynamic daily/weekly/monthly earnings period switcher with real-time charts and metrics.
  • Ledger, payout eligibility, pending requests and operator approval.
  • Fare/time/payment summaries, safety score, trips, receipts, ratings, support and lost items.
Prototype: dynamic earnings periods, payout preview, ledger, insights and trip-history screens.

Native gate: preserve integer-paise amounts, immutable snapshots and distinct cash reports/provider confirmations.

Admin & backend

The existing Admin website and all backend services remain untouched. No migrations, new endpoints, matching changes, provider substitutions, pricing rewrites or database changes are part of this exploration.

Prototype: deliberately isolated. No business API requests are made.

A controlled migration, if you approve the direction

Approve the product journeys.

Review Rider and Captain, including secondary screens. Check compact phones, large text, keyboard states and language wrapping. Capture feature gaps before choosing the final implementation scope.

Prove the native foundation.

Proposed starting point: React Native + Expo development builds. Validate the existing native authentication exchange, session cookies/CSRF, Google Maps, push and Captain location service against the unchanged backend. Reassess Flutter if a required capability fails this proof.

Implement complete vertical slices.

Rider search-to-book and Captain request-to-settlement come first. Then history/money, account/companion, safety/support and onboarding/documents. Move pure TypeScript into shared domain packages; replace DOM, CSS, browser maps and browser-only effects with platform adapters.

Cut over only after feature parity.

Every existing feature needs its API mapping and acceptance evidence. Test real phones, denied permissions, app background/kill/reopen, poor network, quote expiry, duplicate actions and payment status. Keep the existing apps available until the mobile clients pass the parity gates.

The decision now is the experience.

This prototype is a review tool, built with isolated HTML/CSS/JavaScript so it is easy to open and change. It is not a native app, a live backend client, or the final architecture. Approval of this direction does not imply approval to remove any existing feature.
